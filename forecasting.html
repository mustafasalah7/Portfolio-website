Case study 02 · Forecasting engine

Six models compete. Evidence picks the winner.

Instead of choosing a forecasting method by habit, I built an engine that makes six of them prove themselves on months they've never seen, then lets the results decide.

0.97%error in the September backtest
6methods competing
11 moof history in the evaluation window
The problem

A forecast nobody had tested.

Most revenue forecasts are one method, chosen once and never checked. When it misses, nobody knows whether the method was wrong or the month was unusual.

I wanted the opposite: a forecast that has to earn its place against simpler alternatives, every time the data changes.

How it works

Rolling-origin backtesting.

01

Train

Fit every method on the months before a cutoff

02

Predict

Forecast the next month, which the methods haven't seen

03

Score

Compare to what actually happened

04

Roll

Move the cutoff forward one month and repeat

05

Rank

WAPE first, then MAE, then the simpler method wins ties

Same test for everyone: every method is scored on exactly the same evaluation months, so no method gets an easier exam than another.

The contenders

From naive to driver-based.

MethodWhat it assumes
Naive baselineNext month looks like last month. Every other method has to beat this.
3-month averageThe recent average is the best guide.
▶ Weighted 3-monthRecent average, with the latest month counting most. Selected for September.
Exponential smoothingEvery past month matters, decaying with age.
Damped trendThe current trend continues, but flattens out.
Driver-basedRevenue = predicted paid orders × predicted average order value.
Key decisions

Built to be believed.

Baselines

Simple methods stay in the race

A complex model only wins if it beats the naive baseline on the same months. Otherwise the simpler one is used.

Bias

Direction, not just size

The engine tracks whether a method keeps over- or under-forecasting, not only how far off it is.

Ranges

Honest uncertainty

Every forecast ships with a range built from the method's own historical errors.

In-month

A second, lead-aware model

Inside the month, a separate model uses lead volume, conversion timing, weekday patterns and revenue already booked.

Result

Within 0.97% of actual revenue.

Using only data available before September, the engine picked the weighted three-month method and landed within 0.97% of September's actual revenue, across an evaluation window of eleven months.

Under the hood
The selection loop Python · simplified 
def backtest(history, methods, first_cutoff):
    scores = {m.name: [] for m in methods}
    for cutoff in history.months_from(first_cutoff):
        train, actual = history.before(cutoff), history.at(cutoff)
        for m in methods:                     # same months for every method
            scores[m.name].append((m.fit(train).predict(1), actual))
    return scores

def pick_winner(scores, simplicity):
    return min(scores, key=lambda name: (
        wape(scores[name]),                      # 1. weighted absolute % error
        mae(scores[name]),                       # 2. then absolute error
        simplicity[name],                        # 3. then the simpler method
    ))

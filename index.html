My framework

TRUST: how I make AI-assisted numbers trustworthy

The working method I created and use on every analysis and build. AI makes the work fast. TRUST makes sure the speed never costs accuracy.

Trace
T

Profile the sources before writing logic: schemas, join keys and cardinality, grain, timezones, and what each column actually encodes.

Record
R

Cleaning steps, join logic and metric definitions live in a versioned working document that the agents read as their spec. Agents implement written rules; they do not infer them.

Underwrite
U

Control totals against the source, row-level spot checks, impossible-value assertions, and a diff against a manually verified reference dataset whenever a rule changes. Release is blocked until every difference is explained.

Ship
S

The deliverable is built only after the checks pass, then goes through the release gate: tests, real-browser validation and documentation sync.

Track
T

Freshness checks, failure alerts and idempotent retries watch every daily run. Each incident is written back into the record and, where possible, becomes a permanent test.

Direct BI access, no API, no browser

The BI platform offered no API. I reverse-engineered the data calls its own interface makes and rebuilt them on the backend, so a Python query builder runs bounded SQL with no browser session open. Each extraction takes about 8 seconds. The full story ↓

  • Date-bounded windows, inclusive start and exclusive end, in the source's timezone
  • Accepted only if schema, date coverage, row count and control totals all agree
  • Results capped at 200 rows, so aggregates return as one payload with independent totals
  • Conflicting duplicates are rejected, never resolved by silently taking the maximum
  • Rates computed from summed counts, never averaged percentages

WITH message_facts AS (
  SELECT
    message_id,
    template_name,
    min(send_time)                       AS first_send,
    max(send_status = 1)                 AS sent,
    max(is_delivered = 1 OR is_read = 1) AS delivered,
    max(is_read = 1)                     AS read,
    uniqExact(tuple(send_status, is_delivered, is_read)) AS variants
  FROM   analytics.message_send_log
  WHERE  send_time >= toDateTime('<START>', 'Asia/Shanghai')
    AND  send_time <  toDateTime('<END>',   'Asia/Shanghai')
    AND  template_name IN (<APPROVED_TEMPLATES>)
  GROUP BY message_id, template_name
)
SELECT
  toDate(first_send, 'Asia/Shanghai') AS day,
  template_name,
  sum(sent)      AS sent_count,
  sum(delivered) AS delivered_count,
  sum(read)      AS read_count,
  countIf(variants != 1) AS conflicts   -- must be 0
FROM message_facts
GROUP BY day, template_name
ORDER BY day, template_name;

AI-native workflow

I run coding agents like an engineering lead runs a team

Agents build it. Deterministic code runs it. I own the policy. The leverage is in the contract, not the prompt: who owns what, what must never change, and how a fresh session recovers context without guessing.

Agentic loop, with boundaries

I used an agentic loop (inspect, implement, test, refine) to fix a data validator that kept halting the daily run on problems we had already reviewed, which hid new ones behind them. I set the boundaries: regression tests plus a replay of real production exports as the finish line, and a mode where nothing can be published or sent. The fix is a defect register that remembers each reviewed problem, record by record. The daily run itself is deterministic Python with no AI in it: it warns on known issues, emails the data engineering team to investigate any newly missing records, and still blocks on corrupted data. The agent builds and tests. I own the policy.

Two agents, two lanes

One agent owns features, calculations and tooling. The other owns layout and presentation, and never touches calculations or release tooling. Two agents never edit the same branch.

Memoryless handoff

A new session must produce a recovery summary (objective, privacy boundary, plan, open decisions) and wait for approval before writing code.

Invariants as rules

Month-keyed targets, no hard-coded paths, generated folders never treated as source, and docs updated in the same change as logic.

Verify, don't trust

Screenshot QA before any deploy, minimal reproductions for recurring alerts, and metrics checked against the documented formula, not a neighbouring row.

Parallel agent runs

Work fans out to sub-agents in batches of 20 with evidence checked at each stage. Runs are priced before launch so one job cannot exhaust the working budget.

Release gates

Preflight, calculation tests, real-browser checks, a language gate, a documentation-sync gate and a staged release. Production changes go through reviewed pull requests, never direct pushes.

No APImy biggest unlock

The data nobody could see. Now it arrives every morning.

Dead end: I had no API access to the BI platform, and nobody could see WhatsApp data on a daily basis. Nobody knew what to do, and the usual answer was that it couldn't be done.

The move: I traced how the platform's own interface loads its data, then rebuilt those calls on the backend. My agent now reads the platform directly, with no browser session open, nobody logging in and no API.

Now: WhatsApp data lands every morning, on a schedule, in front of the team. Each extraction takes about 8 seconds and is accepted only if schema, dates, row counts and control totals agree.

6 models competeevidence picks the winner

A forecasting engine that runs a contest, not a guess

Most forecasts pick one method and hope. Mine makes six compete: a naive last-month baseline, two moving averages, exponential smoothing, a damped-trend model, and a driver-based model (paid orders × average order value). Each is scored with rolling-origin backtesting: train on earlier months, predict the next, move forward, repeat. The winner is chosen on WAPE, then MAE, then simplicity, with bias and historical error ranges shown beside it. In its September backtest it landed within 0.97% of actual revenue.

A second, lead-aware in-month model adds lead volume, conversion timing, weekday patterns and revenue already booked. I built it in an agentic loop: the agent inspects the pipelines, implements and tests the logic, and every result is challenged against the simple baselines before it is trusted.

Less is moreshort, ordered, direct steps

Rebuilding an agent skill that failed

The first approach put one large, unstructured instruction file inside an existing assistant, and the target customers never came through. The assistant's database was not built for the sales data, and the skill was too long for the agent to follow.

After studying how practitioners write agent instructions, I rebuilt the skill as short, direct steps and restructured how the data enters its database with the colleague who built the assistant. The daily run has finished without a failure since, in 20 to 40 minutes.

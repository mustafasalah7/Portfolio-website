Case study 04 · Agentic AI

AI builds it. Deterministic code runs it.

I used an agentic loop to rebuild a production data validator, with boundaries I set. The daily run that came out of it has no AI in it at all, and that's the point.

Knownissues warn instead of stopping the run
Newlosses emailed to data engineering automatically
Humanowns the acceptance policy
The problem

An old problem hiding new ones.

A defect we had already reviewed kept halting the daily run. Approvals were tied to exact export files, dates and broad signatures, so the same known issue looked new every morning.

Worse, while the run was stopped on an old problem, genuinely new missing records could slip by unseen.

The loop

Inspect → implement → test → refine.

01

Inspect

The agent read the code, scheduler config, docs and past defect decisions

02

Diagnose

Found why approvals didn't survive from one run to the next

03

Implement

A defect register tracked record by record, with decisions reused

04

Test

Regression tests, then a replay of real exports, with nothing published

05

Refine

The replay showed three new missing records, not a repeat. Policy adjusted with me.

Boundaries

The rules I gave the agent.

Scope

What it could read

Code, scheduler configuration, documentation and the history of past decisions. Nothing else.

Finish line

What "done" meant

Regression tests pass, then a replay of real production exports behaves correctly.

Safety

No side effects

Replays ran in a mode where nothing could be published and no message could be sent.

Runtime

Plain Python, every morning.

SituationWhat the daily run does
Known, reviewed issueWarns and keeps running
Newly missing recordsEmails the data engineering team automatically to investigate
Invalid keys or malformed filesBlocks the run

Why no AI at runtime: a daily check has to make the same decision every time. The agent's job was to build and test the rules. Plain code applies them, and the register remembers what was decided.

Under the hood
One entry in the defect register JSON · illustrative 
{
  "record_key": "<record id>",
  "defect": "missing_from_export",
  "first_seen": "2026-10-12",
  "decision": "known_loss_accepted",
  "decided_by": "owner",
  "policy": "warn_only"
}

An illustrative entry. Because decisions are stored per record, a known issue keeps its decision run after run, and anything not in the register is treated as new.

Case study 03 · Biggest unlock

The data nobody could see. Now it arrives every morning.

There was no API, and the usual answer was "it can't be done." I found another way in, and turned it into a daily pipeline nobody has to touch.

The problem

A blocker everyone had accepted.

WhatsApp is a core channel, but its message and registration data only lived inside the BI platform's own screens. There was no API access, so nobody could see WhatsApp performance day to day, and nobody knew how to get it.

Most people would stop there. I didn't.

The move

Use the door the interface already uses.

The platform's screens load their data through internal calls. I traced those calls and rebuilt them as an automated step.

01

Restore session

Headless Chrome reopens a saved, authorised login. Nobody signs in.

02

Fresh token

It takes a new security token for this run.

03

In-session call

A bounded SQL query is sent to the platform's query endpoint from inside that browser session.

04

Validate

The result is accepted only if every check agrees.

Acceptance rules

Fast, but never trusted blindly.

  • Date-bounded windows: inclusive start, exclusive end, in the source's timezone
  • Accepted only if schema, date coverage, row count and control totals all agree
  • Aggregates come back as one capped payload, with independent totals to check against
  • Conflicting duplicates are rejected, never resolved by silently taking the maximum
  • Rates are computed from summed counts, never averaged percentages
Why it matters

From "not doable" to every morning.

This was the difference between hitting the same wall again and actually getting daily WhatsApp data. It now flows into the platform's WhatsApp views with the rest of the morning run, in about 8 seconds per extraction.

Under the hood
Dedupe first, then aggregate SQL · generic names 
WITH message_facts AS (
  SELECT
    message_id, template_name,
    min(send_time)                       AS first_send,
    max(send_status = 1)                 AS sent,
    max(is_delivered = 1 OR is_read = 1) AS delivered,
    max(is_read = 1)                     AS read,
    uniqExact(tuple(send_status, is_delivered, is_read)) AS variants
  FROM   analytics.message_send_log
  WHERE  send_time >= toDateTime('<START>', 'Asia/Shanghai')
    AND  send_time <  toDateTime('<END>',   'Asia/Shanghai')
  GROUP BY message_id, template_name
)
SELECT
  toDate(first_send, 'Asia/Shanghai') AS day, template_name,
  sum(sent) AS sent_count, sum(delivered) AS delivered_count, sum(read) AS read_count,
  countIf(variants != 1) AS conflicts   -- must be 0, or the run is rejected
FROM message_facts
GROUP BY day, template_name;

Table and column names are generic. The pattern is real: one row per message first, so a message can never be counted twice.
